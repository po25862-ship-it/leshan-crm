# 樂善 CRM 物件每日同步

這是僅在使用者 Mac 上執行的桌面同步工具，不會把登入密碼或內部編號放進 GitHub。

## 同步流程

1. 從 4 間店、16 種物件類別下載完整 64 份報表；少一份就中止，不寫入 CRM。
2. 依委託書編號去重並下載詳細資料，補上座落、主建物、附屬建物、公設、車位及管理費。公司公設包含明列的車位坪數，存入 CRM 前會扣除車位，原公設保留於 `commonAreaGrossPing`，並以 `commonAreaBasis: "excluding-parking"` 防止再次匯入時重複扣除。沒有車位坪數或數值矛盾時不自行推測；管理費保留原有月／年／坪等單位。
3. 讀取已登入後台查詢表的「官網點閱」欄位；有數字超連結才標記官網已上架，沒有超連結就標記未上架。頁面涵蓋率不足 90% 時視為登入失效，整批官網狀態不更新。
4. 後台登入有效時，再以 244 個核對過的林口／上龜山路段與地名做跨店關鍵字查詢。關鍵字命中案名或備註不算數；只收完整詳細頁「座落」可驗證的案件。跨里道路只在 115/09 桃園市門牌資料可唯一對應上龜山里別時納入。報表或詳細頁失敗只略過該筆，不據此判下架。
5. 登入 Firebase，先將現有物件存成同步前 JSON 備份。
6. 以委託書編號精準去重更新；保留人工備註，價格異動另寫歷程。
7. 第一次未出現在完整四店報表只記錄，連續第二次未出現才自動標記「暫時不賣」。人工暫停與已售物件不會被自動改回。
   每筆物件另外保留首次掃描出現、首次掃描未見、首次自動暫時關閉及最近掃描時間；舊物件沒有可靠的歷史首次時間時，從此功能啟用後第一次掃描起算，畫面會註明。
   `syncCoverage: "roadKeyword"` 的跨店路段案件不在四店報表的下架判斷範圍內，也不會因單次路段查詢缺席而被誤標暫時不賣。路段掃描只新增或更新有詳細地址驗證的案件。
8. 產生 18 個工作表的 `物件總表_匯出_YYYY-MM-DD.xlsx`、原始 64 份報表、路段查詢結果、詳細頁與同步紀錄。

格局圖可在物件頁上傳並多選套用其他案件。使用者選擇「記住門牌」時，對應圖片會記在該物件的 `floorplanAddressFiles`；每日同步從現有物件建立完整門牌索引，將圖片帶到同地址的新案件，不額外讀取資料庫集合或擴大權限。只有含縣市、行政區、路名及號碼的完整地址能自動配對；樓層與戶別也必須一致。若永久刪除所有記住該門牌的物件，對應關係也會消失，因此永久刪除前應保留備份或另一筆已套用的物件。

## 本機入口

執行 `npm run server` 後開啟 <http://127.0.0.1:8877/>。首次設定會把 CRM 密碼與內部編號存入 macOS 鑰匙圈，並安裝每天 07:30 的 LaunchAgent。CRM 的桌面版「立即同步」按鈕也會開啟這個頁面；手機版不顯示。

每日 07:30 與桌面版「立即同步」都呼叫同一支 `sync.js`，因此都包含路段掃描。若公司後台本月驗證碼尚未更新，四店報表仍可同步，路段掃描會略過並留下紀錄；請在本機入口更新驗證碼後再點「立即同步」。路段範圍見 `road-coverage.txt`；跨里門牌對照使用桃園市 115/09 公開門牌資料的壓縮摘錄 `mixed-road-doorplates-11509.b64`。

### 逾時重試與當日補跑

每份下載遇到逾時、斷線、HTTP 429 或暫時性伺服器錯誤，會在 5／15／30 秒後重試，最多共 4 次。每次連線與下載各有時間限制，部分下載存為暫存檔，成功且驗證後才替換正式檔案。64 份報表任一份失敗時不寫入 CRM，也不把缺檔當成下架。

LaunchAgent 保留每天 07:30，另於載入及每 900 秒執行本機檢查。07:30 前不補跑；之後若今日尚未成功、上次下載逾時或下載階段被中斷，則補跑。當天成功後只讀本機狀態，不下載或讀取 Firestore。手動與排程使用同一把 macOS 程序鎖，避免同時同步。執行期間以 `caffeinate -i` 避免閒置睡眠；不更改電腦永久睡眠設定，關機或手動睡眠時仍須等恢復後才能補跑。

`~/.leshan-property-sync/sync-status.json` 保留進度、錯誤類型及最近成功時間，重啟工具仍可查看。進入 CRM 寫入前會取消可重試標記；若寫入途中出錯，當天不自動重播，以免將未見次數重複累加。若 CRM 已寫完而 Excel 輸出失敗，仍記錄 CRM 成功，不重寫資料。登入資料、驗證碼錯誤或報表內容異常需使用者確認，與網路逾時分開處理。

`node daily.js --check-only` 只顯示本機排程是否需要補跑，不登入、不下載、不寫入 CRM。`node --test download.test.js sync-control.test.js` 使用本機 HTTP 與暫存測試檔，驗證重試、完整檔案替換、補跑、跨程序鎖及寫入後不重播。

### 舊報表自動整理

每天排程及手動同步成功、備份流程結束後，都會執行 `report-retention.js --apply`。它使用相同的程序鎖，且只接受台灣當日的完整成功狀態；同步失敗或執行中不整理。

- 日期資料夾超過 30 天：將 `raw-64`、`raw-details`、`official-status-64`、`road-keywords` 移到 Mac 垃圾桶。
- 超過 90 天：整理該日期的 `CRM同步前備份_YYYY-MM-DD.json`。
- 超過 1 個曆年：整理該日期的 Excel、`snapshot.json`、`road-keyword-summary.json`、`同步紀錄.log`。

同時處理本機 `runs` 與設定的 Google Drive 桌面同步備份資料夾。只辨識固定檔名，保留未知檔案、照片／格局圖、根目錄 `latest-snapshot.json`、程式及登入設定；不跟隨日期資料夾或目標的符號連結。今天及未來日期永遠保留。

Mac 垃圾桶以「樂善同步報表_日期_批次」分組，搬移前先寫 `還原清單.json`，另附 `還原說明.txt`。本機只使用同磁碟搬移；Google Drive 備份使用 macOS 15+ 內建的 `/usr/bin/trash`，由 File Provider 放入該 Drive 垃圾桶，避免先下載數千個雲端原始頁面。每筆保留原位置、回收方式及工具回傳的垃圾桶位置；工作進度也寫入本機狀態檔。失敗保留未搬移的原檔，絕不複製後刪除或清空垃圾桶。垃圾桶仍佔用空間，Drive 容量也須等待桌面同步及雲端垃圾桶處理；不宣稱搬移後立即釋出雲端配額。

`node report-retention.js` 只預覽清單及大小；`--apply` 才執行。最近結果保留於 `report-retention-status.json`，本機同步頁可查看整理時間及保留待確認的數量。

## 安全測試

`npm run test:archive` 只讀取測試封存，不會連線或寫入 Firebase。正式寫入必須明確加上 `--apply-crm`，且 64 份來源全部驗證成功。

## 社區與商圈回填

`node backfill-property-locations.js` 只會預覽可由案名、地址與 A7／A8／A9 路段可靠判斷的結果。確認後使用 `node backfill-property-locations.js --apply` 才會先備份現有資料並補入空白欄位；人工已填內容不會被覆蓋。每日同步也會保留並沿用同一套判斷規則。
